# Overview: 참여자 구분과 QA 역할

## What

제공 요약은 Alpha testing을 내부 참여자 중심, Beta testing을 실제 사용자 중심으로 소개한다. Alpha 참여자를 개발자나 QA 직무로 한정하거나 Beta를 전체 공개 테스트로 규정할 근거는 없다.

| 항목 | Alpha testing | Beta testing |
|---|---|---|
| 참여 주체 | 내부 참여자 | 실제 사용자 |
| 설명의 중심 | 내부 참여자의 역할 | 실제 사용자의 역할 |
| 미확인 참여 조건 | 직무·선정 기준·인원 | 모집 방식·선정 기준·인원 |
| 미확인 운영 조건 | 환경·기간·완료 기준 | 공개 범위·환경·기간·완료 기준 |

## Why

Smoke testing은 새 빌드의 핵심 기능, regression testing은 변경 후 기존 기능, performance testing은 응답 속도가 설명의 중심이다. Alpha/Beta는 참여 주체가 중심이므로 같은 분류 축으로 취급하면 검증 범위를 오해할 수 있다.

다음은 자료의 직접 주장이 아닌 **분석상 주의점**이다.

- 내부 참여자가 확인했다는 이유로 기능·성능·보안 검증 전체를 완료 처리하지 않는다.
- 실제 사용자가 참여했다는 사실만으로 고객·기획 기준 충족을 결론 내리지 않는다.
- 참여자의 소속과 실제 사용 경험을 동일시하지 않는다.

## 특징과 분석 틀

이 개념에 대한 시스템 아키텍처는 제공되지 않았다. 아래 두 축은 이해를 위한 분석 틀이다.

1. **참여자 축:** 내부 참여자인가, 실제 사용자인가.
2. **검증 목적 축:** 핵심 기능, 기존 기능, 응답 속도, 출시 준비 여부 중 무엇을 확인하는가.

> 적용 예시: 실제 사용자가 참여했으며 응답 속도를 확인했다. 참여자 정보와 성능 측정 결과를 각각 남긴다. 영상이 이 조합을 직접 소개했다는 뜻은 아니다.

## 해석의 경계

- 내부 직원이 실제 사용자일 수도 있지만, 집단 중복 허용 여부는 미확인이다.
- Alpha가 반드시 Beta보다 먼저라는 순서나 특정 출시 전후 단계는 확정할 수 없다.
- 어느 집단이 더 많은 결함을 발견하거나 더 높은 품질을 보장하는지도 알 수 없다.
- 자료에서 출시 준비 여부를 확인하는 것으로 설명된 것은 acceptance testing이다. Alpha/Beta 완료를 출시 승인과 동일시할 수 없다.
