# Projects: QA 역할 기록에 적용

아래 프로젝트는 제공 자료에서 도출한 **실습 제안**이며 영상에서 소개된 프로젝트가 아니다.

## 프로젝트 1 — 참여자 구분이 명확한 QA 계획표

작은 기능 하나를 정하고 내부 참여자와 실제 사용자 항목에 검증 목적과 결과 기록 방법을 붙인다.

| 참여자 구분 | 검증 목적 | 수행 과제 | 결과 기록 방법 | 미확인 조건 |
|---|---|---|---|---|
| 내부 참여자 | 작성 | 작성 | 작성 | 작성 |
| 실제 사용자 | 작성 | 작성 | 작성 | 작성 |

- **산출물:** 참여자 구분표, 테스트 목적 목록, 관찰 기록 양식.
- **완료 기준:** 각 결과에서 누가 무엇을 확인했는지 추적할 수 있다.
- **유의점:** 참여자 구분만으로 기능·성능·보안 등 전체 범위를 완료 처리하지 않는다.

## 프로젝트 2 — 동일 기능에 대한 관찰 결과 비교

1. 두 집단이 확인할 공통 기능과 수행 과제를 정한다.
2. 빌드와 수행 조건, 참여자의 소속·사용 경험을 기록한다.
3. 각 관찰의 공통점과 차이점을 근거와 함께 정리한다.
4. 관점 차이와 조건 차이를 구분할 수 없는 항목을 표시한다.

- **산출물:** 공통 수행 과제, 참여자별 관찰 기록, 공통·상이한 발견 사항.
- **완료 기준:** 차이에 대한 설명과 해석 한계가 함께 있다.
- **유의점:** 한 차례의 결과로 특정 집단이 더 우수하다고 일반화하지 않는다.

## 프로젝트 3 — QA 결과와 출시 판단 연결표

| 검토 항목 | 근거 | 판단 | 미확인 항목 |
|---|---|---|---|
| 참여자 구분 | 참여 기록 | 작성 | 작성 |
| 기능 점검 결과 | 수행·관찰 기록 | 작성 | 작성 |
| 응답 속도 측정 | 측정값·조건 | 작성 | 작성 |
| 고객·기획 기준 충족 | 기준과 대응 결과 | 작성 | 작성 |

- **산출물:** 각 판단의 근거와 미확인 항목을 표시한 검토표.
- **완료 기준:** Alpha/Beta 수행 사실이 acceptance 기준 충족의 근거를 대신하지 않는다.
- **유의점:** 위 표 자체가 공식 출시 승인 절차나 충분조건은 아니다.
