# 심화 학습 — 설계와 피드백의 경계

> **근거 범위:** 제공된 dossier는 수집 자료 없이 일반 지식으로 작성된 잠정 정리다. 인물의 기여·저술·개념의 정확한 표현은 확인 필요하다. 해석과 실습 제안은 Kent Beck의 직접적인 발언이나 권고가 아니다.

## 1. 테스트를 interface 탐색에 사용하기

할인 정책에 고객 등급을 추가한다고 가정한다. 호출자에게 필요한 입력과 실패 표현을 먼저 정한다. 핵심 계산에 DB 조회가 꼭 필요한지 질문하고, 조회 결과를 값으로 전달하는 설계와 비교한다. 테스트하기 어렵다는 사실만으로 설계 결함을 단정하지 않는다.

## 2. Unit과 integration의 책임 나누기

| 검증 대상 | 수단 | 놓칠 수 있는 것 |
|---|---|---|
| 정책과 경계값 | 빠른 unit test | 실제 저장소 제약 |
| unique 제약·transaction rollback | 실제 DB integration test | 운영 규모·모든 장애 |
| 외부 API 오류 매핑 | stub 기반 unit test | 실제 계약 불일치 |
| 실제 요청·응답 호환성 | 계약 검증 또는 실제 연동 | 장기 운영 안정성 |

mock은 우리가 가정한 응답을 돌려줄 뿐 실제 시스템의 동작을 증명하지 않는다. 별도 테스트 데이터와 환경을 사용한다.

## 3. 구조 변경 분리 실험

1. 현재 동작의 보호 테스트를 확보한다.
2. 함수 추출이나 이름 변경만 수행하고 테스트한다.
3. 동작 변경을 별도 diff로 만든다.
4. 버그가 나면 어느 변경이 원인인지 좁힐 수 있는지 확인한다.

구조와 동작 변경을 함께 해야 한다면 이유와 검증 범위를 기록한다. private 함수나 내부 호출 횟수를 고정한 테스트가 변경을 막는지 점검한다.

## 4. 팀 전달 루프 관찰

테스트 실행 → review → 통합 → 배포의 실행 시간과 대기 시간을 구분한다. Pair Programming·CI·작은 release가 어느 지연을 줄일 수 있을지 가설을 세운다. XP의 정확한 실천 구성과 판본 차이는 원문 확인이 필요하다.

## 회고 질문

- 실패 원인을 찾기까지 얼마나 걸렸는가?
- 테스트 수정이 요구 변경 때문인가, 내부 구현 결합 때문인가?
- 공개 API·migration·보안·복구 설계에 별도 검토가 필요한가?
- 한 사례의 개선을 팀 전체 생산성으로 확대하고 있지는 않은가?
