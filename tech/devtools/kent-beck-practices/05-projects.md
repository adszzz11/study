# Projects — 실전 적용 제안

> **근거 범위:** 제공된 dossier는 수집 자료 없이 일반 지식으로 작성된 잠정 정리다. 인물의 기여·저술·개념의 정확한 표현은 확인 필요하다. 해석과 실습 제안은 Kent Beck의 직접적인 발언이나 권고가 아니다.

## 1. Legacy 코드의 안전한 변경

- **범위:** 실제 변경 요청이 있는 작은 함수·모듈 하나.
- **절차:** characterization test로 현재 동작 기록 → 의도한 규칙과 우연한 동작 구분 → 구조 정리 → 기능 변경.
- **주의:** 현재 동작을 기록했다고 올바른 요구로 승인된 것은 아니다. 의심스러운 동작은 변경 여부를 별도로 판단한다.
- **결과물:** 보호 테스트, 구조·동작별 diff, 남은 불확실성 목록.
- **완료 기준:** 기존 보호 테스트와 새 요구 테스트가 통과하고 변경된 동작을 설명할 수 있다.

## 2. Backend 정책 로직 개선

- **범위:** 요금·권한·주문 상태 중 하나의 정책.
- **절차:** 규칙표 작성 → 정상·경계·실패 사례 정의 → 빠른 정책 테스트 → 실제 DB의 제약·transaction 검증.
- **결과물:** 규칙별 테스트, 정책과 I/O 책임 구분, 실제 저장소에서 관찰한 실패 사례.
- **완료 기준:** 각 규칙의 검증 위치를 설명하고 mock으로 확인하지 못한 영역을 명시한다.

## 3. 팀의 피드백 병목 실험

- **범위:** 작은 기능 한 개의 테스트부터 배포까지.
- **절차:** 단계별 실행·대기 시간 기록 → 가장 긴 병목 선택 → 한 가지 개선 → 비슷한 크기의 후속 작업과 비교.
- **결과물:** 시간 기록표, 개선 내용, 전후 차이와 교란 요인.
- **완료 기준:** 실제 병목과 측정 한계를 설명한다. TDD 도입만으로 성과를 설명하지 않는다.

| 기록 항목 | 개선 전 | 개선 후 | 해석 시 주의점 |
|---|---|---|---|
| 테스트 실행 시간 | 측정값 | 측정값 | 환경·대상 범위 |
| 실패 진단 시간 | 측정값 | 측정값 | 실패 유형 차이 |
| review·통합 대기 | 측정값 | 측정값 | 팀 일정·작업 크기 |
| 배포 대기 | 측정값 | 측정값 | release 정책 |
