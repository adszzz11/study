# Projects: 실무 적용

## 1. 주문·환불 backend

- **목표:** 주문 상태와 환불 규칙을 HTTP, ORM, 결제 API에서 분리한다.
- **구성:** domain model, Use Cases, persistence adapter, payment adapter.
- **검증:** domain rule은 외부 연결 없이, 저장·결제는 integration test로 확인한다.
- **완료 기준:** 정책 변경이 HTTP·ORM 코드의 불필요한 수정을 요구하지 않는다. 실패·재시도 시나리오도 설명할 수 있다.
- **주의:** transaction과 외부 결제 실패를 interface 뒤로 숨겼다는 이유만으로 해결했다고 간주하지 않는다.

## 2. 기존 service의 점진적 refactoring

- **목표:** 계산·조회·알림 책임을 실제 변경 이유에 따라 분리한다.
- **방법:** 현재 행동을 보호하는 테스트를 확보하고 자주 바뀌는 부분부터 추출한다.
- **완료 기준:** 특정 정책 변경이 관련 없는 I/O 수정을 요구하지 않는다.
- **주의:** 일괄 재작성보다 작은 변경으로 경계의 효용을 확인한다.

## 3. 동일 기능의 두 가지 설계 비교

dossier의 마지막 항목이 중간에 끊겨 있어, 다음 실험 절차는 앞선 학습 지침을 바탕으로 보완한 제안이다.

- **목표:** 단순 CRUD와 Clean Architecture를 동일 요구사항으로 구현한다.
- **고정 조건:** 같은 언어, 기능, 오류 처리, 테스트 시나리오를 사용한다.
- **변경 실험:** 할인 규칙 추가 → 저장소 교체 → CLI 진입점 추가를 각각 수행한다.
- **산출물:** 변경 diff, 테스트 결과, 관찰표, 유지하거나 제거할 경계의 이유.
- **완료 기준:** 각 설계가 유리한 변경과 불리한 변경을 하나 이상 설명한다.

| 평가 항목 | 단순 CRUD | Clean Architecture |
|---|---|---|
| 초기 구현·이해 비용 | 실측·기록 | 실측·기록 |
| 변경 파일 수·추가 코드량 | 실측·기록 | 실측·기록 |
| 테스트 준비와 외부 연결 요구 | 실측·기록 | 실측·기록 |
| 오류 처리·복구의 명확성 | 관찰·기록 | 관찰·기록 |

구현 순서와 학습 효과가 결과에 영향을 줄 수 있다. 작은 실험의 결과를 일반적 생산성 향상으로 해석하지 않는다.
