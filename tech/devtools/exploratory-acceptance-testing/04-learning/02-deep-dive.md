# 심화: 발견 결과를 출시 판단에 연결

## 핵심 질문

발견한 버그가 어떤 기준에 영향을 주는가? 연결이 불명확하다면 무엇을 더 확인해야 하는가? 아래 기록 방식은 정의에서 도출한 실습 제안이다.

## 검토표

| 기록 대상 | 적을 내용 | 학습 목적 |
|---|---|---|
| 탐색 관찰 | 사용 과정·환경·문제 | 발견 구체화 |
| 기준별 확인 | 실제 기준·출처·증거·결과 | 판단 근거 명시 |
| 연결 | 관찰 ID와 기준 ID, 영향 | 발견과 판단 연결 |
| 불확실성 | 미확인 기준·불명확한 영향 | 결론 범위 제한 |

```text
[학습용 빈 양식]
관찰 ID: E-___
관찰 사실:
관련 기준 ID: A-___ / 연결 미확인
기준 원문 및 출처:
기준별 확인 결과와 증거:
관찰이 기준에 미치는 영향:
추가 확인할 사항:
출시 준비 판단에 반영한 근거:
```

연결할 기준이 아직 없다는 이유로 버그를 무시하지 않는다. 기준 보완이 필요한지 별도로 검토하되, 수행자가 새로 만든 기준을 기존 고객 요구로 표시하지 않는다.

## 과도한 결론 고치기

| 과도한 결론 | 근거 범위에 맞는 표현 |
|---|---|
| 버그를 못 찾았으니 출시 가능 | 이번 탐색 범위에서 버그 미발견. 실제 기준은 별도 확인 필요 |
| 기준 통과로 모든 사용 상황 보장 | 확인한 기준은 충족. 미탐색 상황까지 보장하지 않음 |
| 고객 기준이므로 고객만 테스트 가능 | 기준의 출처를 뜻하며 필수 수행자는 자료에 없음 |
| 탐색을 반드시 먼저 수행 | 연결 구조는 제안이며 고정 순서는 자료에 없음 |

## 완료 확인

- [ ] 실제 관찰과 해석을 구분했다.
- [ ] 모든 연결에 영향 설명 또는 미확인 사유가 있다.
- [ ] 최종 판단에 사용한 근거와 남은 불확실성을 설명했다.
