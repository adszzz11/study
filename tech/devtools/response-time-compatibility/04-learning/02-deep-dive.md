# 심화 학습: 비교 조건과 결과 해석

## 동일 시나리오로 두 축 교차하기

환경별로 작업이 다르면 차이가 환경 때문인지 시나리오 때문인지 구분하기 어렵다. 시나리오와 기대 결과를 고정한 뒤 기능 결과와 시간 관찰값을 나란히 놓는다.

| 기능 관찰 | 시간 관찰 | 해석 범위 |
|---|---|---|
| 기능 동작 | 기준 검토 필요 | 동작 성공과 속도 판정을 분리 |
| 특정 환경에서 실패 | 측정 가능 여부 함께 기록 | 해당 환경·조건의 문제로 보고 |
| 환경별 기능·시간 차이 | 차이 관찰 | 원인 확정은 추가 조사 필요 |

이는 가능한 분류다. 자료에서 실제 장애 사례가 발견되었다는 뜻은 아니다. 기능이 완료되지 않았다면 정의한 완료까지의 시간을 정상 측정값으로 채우지 말고 실패 상태와 관찰 범위를 적는다.

## 변경 전후 비교

1. 이전·이후 빌드의 식별 정보를 남긴다.
2. 시나리오, 기기·브라우저 조합, 측정 구간을 맞춘다.
3. 조건이 달라진 부분은 별도 표시한다.
4. 기능 변화와 시간 변화를 각각 기록한다.
5. 차이가 보이면 재현 조건을 남기고 추가 조사 대상으로 정리한다.

여러 번 관찰한다면 각 실행값과 조건을 보존한다. 반복 횟수·집계 방식·허용 기준은 이 자료에서 정해지지 않았으므로 선택한 방법을 명시한다. 단일 관찰을 전체 성능의 대표값으로 일반화하지 않는다.

## 관찰에서 판정으로

- **관찰**: 어떤 조건에서 어떤 동작과 시간이 확인되었는가.
- **판정**: 그 결과가 합의된 acceptance 기준을 충족하는가.
- **원인**: 왜 차이가 발생했는가. 관찰만으로 확정하지 않는다.

기준 부재와 기준 미충족을 구분한다. 사용성·접근성·보안은 별도 검증 결과가 필요하며 이 표의 성공으로 대체할 수 없다.

## 연습 문제

- 일부 브라우저만 성공했다면 보고서에 어떤 범위를 명시해야 하는가?
- 변경 후 시간이 달라졌지만 네트워크도 바뀌었다면 어떤 결론을 유보해야 하는가?
- 합격선이 없다면 측정값과 출시 판정을 어떻게 분리할 것인가?
