# 심화: 이벤트에서 근거까지

## 상태 모델 설계

학습용 기본 전이는 `queued → running → succeeded | failed`다. 성공은 검증 통과를 포함한다. 검증이 비동기라면 `validating` 상태를 추가하고, 실패·취소·재시도의 정책을 명시한다.

```json
{
  "event_id": "E17",
  "task_id": "T2",
  "attempt_id": "A2",
  "agent_id": "agent-example",
  "state": "succeeded",
  "occurred_at": "2026-11-27T00:00:00Z",
  "received_at": "2026-11-27T00:00:02Z",
  "validation": "passed"
}
```

이는 제안 스키마다. 영상의 실제 이벤트 형식이 아니다. 검증 근거·산출물 참조와 상태 순서 또는 버전을 추가하면 조회와 재집계에 도움이 된다.

## 집계 정확성

| 상황 | 설계 규칙 | 점검 방법 |
|---|---|---|
| 중복 수신 | event_id 기준 중복 제거 | 같은 이벤트 두 번 입력해 집계 불변 확인 |
| 역순 수신 | 작업 버전·순서 기준 최신 상태 결정 | 늦은 running이 succeeded를 덮지 않는지 확인 |
| 재시도 | task와 attempt 구분 | 실패 시도와 최종 성공 작업을 별도 집계 |
| 취소 | 분모 포함 정책 명시 | 제외 시 범위 변경 이력 표시 |
| 작업 추가 | 분모 버전·기준 시점 보존 | 비율 하락 원인을 설명 |

완료 작업 수는 성공 attempt 수의 단순 합이 아니다. task ID별 최종 검증 상태로 계산한다. 실패 작업 수와 실패 시도 수도 별도 Metric이다.

## 두 가지 Progress

```text
개수 기준 = 검증 통과 작업 수 / 전체 대상 작업 수
작업량 기준 = 검증 통과 작업의 예상 작업량 합 / 전체 예상 작업량 합
```

가중치는 실행 전에 정하고 변경 이력을 남긴다. 둘 다 부분 작업 품질이나 실제 소요 시간을 자동으로 보증하지 않는다. 분모가 0이면 `N/A`, 분모가 미확정이면 비율 산출 불가로 표시한다.

## 데이터 신선도와 근거 조회

- 발생 시각·수신 시각·화면 갱신 시각을 구분한다.
- 예를 들어 마지막 수신 이후 60초가 지나면 `stale`로 표시하는 정책을 실습한다. 60초는 실습값이며 제품의 기준이 아니다.
- 이벤트가 없다는 이유만으로 작업 중단으로 표시하지 않는다. 유휴·수집 지연·연결 단절을 판별할 추가 신호가 필요하다.
- 패널 → 집계 대상 작업 → 상태 이벤트 → 산출물·검증 결과로 이동하게 한다.
- 그래프 edge는 위임·의존·통신 중 의미를 명시하고 관계 변경의 근거 이벤트를 연결한다.

## 실험 과제

동일한 이벤트를 재생해 동일한 집계를 복원한다. 중복·역순·재시도·작업 추가·수집 지연을 주입하고, 수치와 경고가 정의한 규칙을 따르는지 확인한다.
