# Overview: 화면 비교와 반복 수정

## What

화면을 피드백으로 다시 사용하는 개발 과정이다. 단일 제품이나 검증된 자동화 도구의 이름이 아니다. 텍스트의 “완료”와 화면에서 확인되는 개선을 구분한다.

## Why

“더 비슷하게”라는 요구는 변경 범위가 모호하다. 위치·간격·색상·전환 순서처럼 관찰 가능한 차이로 바꾸면 수정과 결과를 연결할 수 있다. 모션그래픽은 특정 시점의 외형이 비슷해도 시작 시점과 움직임은 다를 수 있다.

## 특징과 관찰 한계

| 요소 | dossier의 관찰 | 확인되지 않은 내용 |
|---|---|---|
| 수정 인터페이스 | Claude 채팅의 여러 수정 요청 | 요청 전문, 실제 코드 변경 |
| 명령 단서 | 일부 보이는 `/reanimate` | 공식 명령 여부, 별도 도구 여부, 동작 |
| 시각적 입력 | 화면 녹화 첨부 | 처리 방식 |
| 반복 관찰 | 다시 녹화한다는 자막 | 같은 조건의 재검증 여부 |
| 병렬 비교 | 유사한 웹 화면 두 개 | 기준·결과 관계, 정량적 차이 |
| 자동화 단서 | 자동 수정 언급 | 감지·수정·검증 범위와 성공 여부 |
| 상태 표시 | `CMS Drafts`, `417 / 417`, 찬 진행 막대 | 지표 정의와 실제 품질 |

요약의 주요 시점은 00:14와 00:34이나 개별 관찰이 어느 시점인지 상세히 매핑되지 않는다. 이를 임의로 배정하지 않는다.

## 개념적 아키텍처

```text
수정 요청 → 결과 생성·변경 → 화면 관찰·녹화 → 차이 판단
    ↑                                             │
    └──────────────── 다음 수정 요청 ──────────────┘
```

이 도식은 분석 모델이며 영상 내부 구현을 복원한 것이 아니다.

1. 요청과 관찰: 대상·차이·확인 방법을 명시한다.
2. 관찰과 변경: 발견한 차이와 수정 범위를 연결한다.
3. 변경과 검증: 실행 완료와 결과 개선을 따로 확인한다.

## 비교 축

| 축 | 질문 | 필요한 관찰 |
|---|---|---|
| Layout | 위치·크기·간격이 맞는가? | 동일 viewport 정지 화면 |
| 시각 표현 | 색상·타이포그래피·형태가 맞는가? | 동일 state·배율 화면 |
| Motion | 시작·종료·이동 과정이 맞는가? | 같은 시작 조건의 녹화 |
| 상호작용 | 같은 입력이 같은 상태로 이어지는가? | 입력부터 결과까지 재현 |
| 수정 영향 | 다른 부분이 바뀌었는가? | 변경 전후 동일 구간 |

이 비교 축은 실습 제안이다. 영상에서 이 기준을 실제 측정했다는 의미는 아니다.
