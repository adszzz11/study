# 시작하기: 작은 Research 작업 인계

## 목표와 준비

한 클라이언트의 기록을 다른 클라이언트가 원본 재입력 없이 찾고 사용하는지 검증한다. 아래는 제품 지원이 확인된 설치 절차가 아니라 **실험 설계**다. 먼저 공식 연결·읽기·쓰기 절차가 있는지 확인하고, 없다면 설계 단계에서 멈춰 미검증으로 기록한다.

민감정보 없는 원본 파일 하나, 파생 요약 하나, 관련 조직 엔터티 하나를 준비한다. 실제 고객 데이터나 메시지 발송은 필요하지 않다.

## 1. 메모리 단위와 관계 정의

```yaml
# 학습용 기록 예시: 제품 API나 공식 스키마가 아님
file: research-001
revision: 1
output: summary-001
entity: example-org
relations:
  - summary-001 derived_from research-001
  - research-001 about example-org
```

관계의 의미와 근거를 설명한다. 노드 수보다 원본으로 추적 가능한 관계가 중요하다.

## 2. 작업 인계 실험

1. 클라이언트 A가 원본에 근거한 요약과 원본 참조를 기록한다.
2. 별도 클라이언트 B에는 원본·요약을 붙여 넣지 않고 기록 조회를 요청한다.
3. B가 찾은 요약, 원본 참조, 사용한 revision을 기록한다.
4. 원본의 사실 하나를 수정해 revision 2로 만든다.
5. B가 재조회할 때 변경과 기존 요약의 상태를 식별하는지 확인한다.

첫 조회는 공유 접근을, 수정 뒤 조회는 갱신 전파를 시험한다. A의 쓰기 성공도 별도로 저장 결과에서 확인한다. 읽기 성공만으로 쓰기·동기화까지 통과 처리하지 않는다.

## 3. 관찰 기록과 판정

| 항목 | 통과에 필요한 증거 |
|---|---|
| 기록 | A가 저장한 내용과 식별자를 다시 조회 |
| 공유 조회 | B가 원본 재입력 없이 동일 기록을 찾음 |
| 출처 | B의 결과에서 원본과 파생 관계를 추적 |
| 최신성 | revision 2와 이전 요약 상태를 구분 |

실행 시각·클라이언트 버전·입력·조회 결과·대기 시간을 남긴다. 결과는 `통과 / 실패 / 미검증`으로 구분한다. 실행하지 못한 항목은 실패로 단정하지 않는다.
