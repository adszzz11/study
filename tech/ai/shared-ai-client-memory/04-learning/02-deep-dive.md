# Deep Dive: 메모리 신뢰성과 에이전트 운영

## 정확성과 최신성을 분리하기

아래 항목은 확인된 제품 기능이 아닌 평가 기준이다. 정답 자료와 기대 결과를 먼저 정하고 관찰 결과를 대조한다.

| 실험 | 입력 | 확인할 증거 |
|---|---|---|
| Entity resolution | 이름이 같은 서로 다른 조직 두 개 | 식별자를 구분하고 근거를 제시 |
| 모순 처리 | 출처가 다른 상충 기록 | 차이를 드러내고 임의 통합하지 않음 |
| 버전 구분 | 수정 전·후 원본과 이전 요약 | 사용한 버전 및 오래된 결과물을 식별 |
| Provenance | 원본에서 파생된 출력물 | 답변 → 출력물 → 원본 추적 |
| 동시 수정 | 두 클라이언트가 같은 기록 수정 | 덮어쓰기·병합·거부 결과와 이력 확인 |

갱신 지연과 잘못된 답변은 서로 다른 문제다. 수정 시각·조회 시각·반영 시각을 기록하고, 허용 지연은 사용 목적에 맞춰 실험 전에 정한다.

## 조회 기술에 대한 추정을 피하기

Graph DB는 저장 방식, vector search는 검색 방식, GraphRAG는 그래프를 활용한 검색·생성 접근에 관한 용어다. 그래프 UI만으로 어느 기술을 쓰는지 판정할 수 없다. MCP·API·파일 동기화도 가능한 연결 방식의 예일 뿐 Orbit Agents의 확인된 스택이 아니다.

## 조직도와 권한 분리

Content·Marketing·Research라는 화면 분류가 접근 통제를 뜻하지 않는다. 시험용 기록을 부서별로 나누고 허용된 조회와 차단되어야 할 조회를 각각 검증한다. 역할 변경 후 권한이 실제로 바뀌는지도 관찰한다. 정책 문서와 접근 로그가 없다면 권한 보장을 주장하지 않는다.

## 실행 증거와 성과 대조

Lead Finder나 Email Outreach Agent의 평가는 다음 단위를 따라간다.

```text
run_id → 입력 → 조회한 메모리와 버전 → 도구 호출
       → 결과물 → 성공·실패 판정 → 대시보드 집계
```

- 성공 조건을 사전에 정의한다. 결과 생성과 실제 외부 작업 완료를 구분한다.
- 실패·재시도를 별도로 기록하고 중복 집계 여부를 확인한다.
- 대시보드 수치를 개별 실행 기록으로 다시 계산한다.
- Outreach 실습은 발송 없는 초안 또는 시험 환경에서 시작한다.
