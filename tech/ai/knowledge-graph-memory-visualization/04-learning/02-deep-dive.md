# Deep Dive: 공유 메모리와 운영 연결 검증

## 1. 관계의 provenance 설계

아래는 실습용 schema 예시이며 제품 API나 저장 형식이 아니다.

```json
{
  "source": "O1",
  "relation": "uses_evidence",
  "target": "F1",
  "evidence_location": "section-2",
  "source_version": "v1",
  "created_by": "agent-research",
  "run_id": "run-001",
  "review_status": "unverified"
}
```

ID는 노드의 정체성, version은 내용의 시점을 나타낸다. 같은 엔터티의 이름이 달라도 하나로 병합할 근거가 있는지 검토한다. 모델이 추출한 관계와 사람이 확인한 관계도 구분한다.

## 2. 두 클라이언트의 변경 실험

| 단계 | 작업 | 기록할 증거 |
|---|---|---|
| 기준 | A·B가 같은 자료 조회 | 자료 ID, 버전, 조회 시점 |
| 갱신 | A가 일정 C 변경 | 이전·새 값, 작성자, 변경 버전 |
| 재조회 | B가 다시 조회 | 최신 내용 반영 여부, 지연 |
| 충돌 | A·B가 같은 기준 버전에서 다른 값 작성 | 두 값, 충돌 감지·해결 정책 |
| 삭제 | 자료 제거 후 연결 조회 | 남은 관계와 파생 출력물의 상태 |

예시 정책으로 충돌한 두 값을 보존하고 검토자가 해결하게 할 수 있다. 이는 설계 선택이며 Orbit Agents의 동작을 뜻하지 않는다. 오래된 값이 유지되었을 때 저장·검색·캐시·맥락 전달 중 어느 단계인지 분리해 조사한다.

## 3. 운영 화면을 질문에 연결

| 화면 | 답해야 할 질문 | 별도 확인할 사항 |
|---|---|---|
| 조직도 | 누가 어느 부서에 배치됐는가? | 실제 권한·위임과 일치하는가? |
| 대시보드 | 어떤 성과를 어떻게 측정했는가? | 지표 정의와 실행 기록이 있는가? |
| 메모리 그래프 | 어떤 정보가 어떤 근거와 연결되는가? | 원문·버전·출력물 추적 가능한가? |

같은 화면 집합에 존재한다는 이유로 데이터가 연결되었다고 가정하지 않는다. 출력물 ID와 run ID로 실제 실행 기록을 찾을 수 있는지 확인한다.

## 4. 규모와 접근 제어

- 노드 수를 단계적으로 늘리고 같은 질문의 성공률과 탐색 시간을 기록한다.
- 필터·검색·주변 노드 확장이 제공되는지는 먼저 확인한다.
- 권한이 다른 클라이언트로 조회해 원문뿐 아니라 노드 이름·관계에서도 비공개 정보가 노출되는지 확인한다.
- 공개 실습에는 가상 자료만 사용하고 실제 개인정보·인증정보를 넣지 않는다.
