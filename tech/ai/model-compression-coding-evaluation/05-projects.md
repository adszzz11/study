# Projects: 실전 검증

아래 프로젝트는 실습 제안이며 완료된 결과가 아니다.

## 1. 압축 전후 코딩 평가 harness

- **목표:** 파일 크기 변화와 코드의 실제 동작 변화를 함께 측정한다.
- **입력:** 변환 관계가 확인된 모델 쌍, 고정 문제 집합, 동일 생성 설정.
- **처리:** 생성 → 분리된 실행 환경에서 테스트 → 실패 원인 분류.
- **산출물:** 문제·시도별 통과 여부, 원본 출력, 생성 시간, 최대 메모리, 실행 조건.
- **완료 기준:** 다른 실행에서도 같은 절차를 재현할 수 있도록 설정·버전·테스트를 보존한다.

관계를 확인할 수 없으면 압축 효과가 아닌 모델 간 관찰 차이로 보고한다. 테스트 harness의 코드 추출 규칙과 timeout도 동일하게 적용한다.

## 2. 노트북 실행 가능성 검증

- **목표:** 특정 장치에서 목표 작업을 감당하는지 확인한다.
- **입력:** 장치 사양, 호환 runtime, 식별된 모델 파일, 길이가 다른 코드 생성 prompt.
- **처리:** 짧은 생성부터 시작해 입력·출력 길이를 늘리고 로딩·실패 지점·시간·메모리를 기록한다.
- **산출물:** 길이별 실행 가능 범위와 품질·비용 표.
- **완료 기준:** 사전에 정한 업무 품질, 응답 시간, 메모리 한도 충족 여부를 판정한다.

한 번의 실행 성공을 모든 노트북에 일반화하지 않는다. 실제 파일을 확보하지 못하면 준비 단계로 남긴다.

## 3. 회사 문서 로컬 처리 PoC

- **목표:** 로컬 처리 구상을 문서 작업의 정확도와 처리 경로로 검증한다.
- **입력:** 비민감 샘플 문서, 정답 근거가 있는 질문, 데이터 흐름도.
- **처리:** 문서 입력·전처리·추론·로그 저장 위치 및 외부 통신을 확인하고 답변의 문서 부합성을 평가한다.
- **산출물:** 문서 QA 결과, 근거 위치, 처리 경로와 관찰 범위, 라이선스 확인 기록.
- **완료 기준:** 업무 정확도와 로컬 처리 요건을 각각 충족하는지 판단한다.

외부 통신이 관찰되지 않은 한 번의 실행만으로 모든 조건에서의 비전송을 보장하지 않는다. 코딩 평가와 문서 QA는 별도로 운영한다.
