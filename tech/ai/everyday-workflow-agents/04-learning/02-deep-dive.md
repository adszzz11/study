# Deep Dive: 지속 실행과 역할 분리 평가

## 1. 비동기 상태 설계

사용자 부재 중 이어갈 작업 하나에 아래 상태를 적용해 본다. Dots나 OpenClaw의 실제 상태 체계가 아닌 평가용 설계다.

```text
requested → running → completed
                ├→ needs_input → running
                └→ failed
```

| 상태 | 기록할 정보 |
|---|---|
| requested | 작업 ID·요청·기한·완료 조건 |
| running | 시작 시각·현재 단계·마지막 갱신 |
| needs_input | 누락 정보·질문·대기 시작 시각 |
| completed | 결과 위치·완료 조건 충족 근거 |
| failed | 실패 원인·재시도 판단에 필요한 정보 |

중복 요청을 같은 ID로 식별할 수 있는지, 중단 뒤 어떤 입력부터 다시 시작할지 점검한다. 제품의 retry·복구 지원을 주장하는 것은 아니다.

## 2. 역할 분리 비교

동일 자료와 완료 조건으로 두 실행을 비교한다.

- **통합 실행:** 한 번에 조사·작성·검토 요청.
- **분리 실행:** 연구자는 근거 목록, 작성자는 근거 기반 초안, 검토자는 원문에 없는 주장과 누락 목록 작성.

| 실행 | 누락 수 | 근거 없는 주장 수 | 검토 후 수정 항목 수 |
|---|---|---|---|
| 통합 | 실측 전 | 실측 전 | 실측 전 |
| 분리 | 실측 전 | 실측 전 | 실측 전 |

역할 분리가 항상 좋다고 가정하지 않는다. Hermes에서 자동 인계나 검토 독립성이 확인된 것은 아니다.

## 3. 메모리 요구 정의

| 정보 | 설계상 취급 | 실제 도구에서 확인할 것 |
|---|---|---|
| 반복되는 문서 형식 선호 | 지속 기억 후보 | 저장·조회·수정·삭제 방식 |
| 이번 작업의 일정 후보 | 작업 한정 입력 | 종료 후 보존 여부 |
| 역할 간 공유할 근거 | 필요한 역할에 전달 | 공유 범위와 접근 권한 |

메모리 설정 화면은 보존 기간이나 역할 간 공유의 증거가 아니다. 도구가 삭제·수정을 지원하는지 별도로 확인한다.

## 4. 종료 판단

작업을 시작한 횟수와 완료 조건을 충족한 횟수를 따로 센다. 입력 대기·실패를 성공에 포함하지 않고, 실패 사례도 평가 기록에 남긴다.
