# 심화 학습: 코딩 품질과 데이터 흐름

## 1. 비교 가능한 평가 설계

비교 가능한 배포물이 확보됐을 때만 수행한다. 같은 계열인지, 변환이나 설정 차이가 무엇인지 확인한다. 비교 조건이 다르면 용량 감소의 효과라고 단정하지 않는다.

1. 업무를 대표하는 코딩 과제와 테스트를 고정한다.
2. 모델 식별자·파일·장비·runtime·prompt·생성 설정·입력 길이를 기록한다.
3. 두 배포물에 동일 과제를 실행하고 생성 코드와 로그를 보관한다.
4. 정답 여부, 테스트 통과 수, 응답 시간, 자원 사용량을 기록한다.
5. 반복 측정의 변동과 실패 사례를 함께 보고한다.

| 실험 ID | 모델/설정 | 파일 크기 | 테스트 통과/전체 | 응답 시간 | RAM/VRAM | 실패 사례 |
|---|---|---|---|---|---|---|
| 작성 예정 | 미확인 | 미측정 | 미측정 | 미측정 | 미측정 | 미확인 |

크기가 줄었다는 관측과 업무 품질을 유지한다는 판단을 별도로 작성한다. 제공 자료에는 품질 결론을 확정할 결과가 없다.

## 2. 문서 처리 경로 검증

민감정보가 없는 샘플 문서만 사용한다. 아래는 영상 구현이 아니라 검증할 지점이다.

```text
샘플 문서 → 입력 UI/전처리 → 추론 → 후처리 → 결과 저장
각 단계: 실행 위치 / 전송 대상 / 저장 위치 / 로그 증거
```

- 모델 다운로드 단계와 문서 추론 단계의 통신을 구분한다.
- 입력 UI, 원격 API 호출, telemetry, 결과 저장 경로를 실제 구성에서 확인한다.
- 통신 관찰 방법·기간·범위를 남긴다. 관측되지 않았다는 결과를 모든 조건의 외부 전송 부재로 일반화하지 않는다.
- 외부 전송이나 저장 위치가 미확인이면 “전체 로컬 처리 검증 완료”로 표시하지 않는다.

## 3. 해석을 보류할 항목

세 가지 값의 정확한 정의가 없으므로 특정 quantization 기법을 구현하는 튜토리얼로 확장하지 않는다. 5.9GB를 메모리 요구량으로 간주하거나, 장비 사양 추천의 근거로 쓰지 않는다.
