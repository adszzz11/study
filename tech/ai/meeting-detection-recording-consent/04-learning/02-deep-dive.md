# 심화 학습 — 세션 경계와 데이터 lifecycle

## 비동기 이벤트와 승인 유효성

아래 항목은 구현 검토 제안이다. Damso의 실제 정책으로 해석하지 않는다.

| 상황 | 정할 정책 | 검증 포인트 |
|---|---|---|
| 질문 중 회의 종료 | pending 무효화 | 늦은 승인으로 시작하지 않음 |
| 반복 감지 | session별 요청 병합 | 질문·시작 중복 방지 |
| 이전 UI에서 승인 | request ID·session ID·만료 확인 | 다른 세션에 승인 재사용 불가 |
| 무응답 | 미시작, 만료 후 재질문 여부 명시 | timeout이 승인으로 바뀌지 않음 |
| 승인과 종료 동시 발생 | 전이 직렬화·원자적 조건 확인 | 종료된 session 시작 차단 |
| recorder 시작 실패 | 실패 상태와 재시도 정책 | 승인 범위·유효기간 재검사 |

`session_id`, `request_id`, 승인 범위, 유효기간을 함께 검사한다. 승인 확인과 recorder 호출 사이의 경합도 다룬다. 동의 상태가 바뀌거나 회의가 끝났을 때 중지·삭제를 어떻게 처리할지도 별도로 정의한다.

## 데이터별 경계

| 데이터 | 생성 시점 확인 | 보관·삭제 설계 질문 |
|---|---|---|
| 감지 입력 | 승인 전 사용 여부 | 오디오·앱 상태 접근, 임시 버퍼와 저장 여부 |
| 원본 오디오 | 녹음 시작 이후인지 | 처리 위치, 보존 기간, 삭제 범위 |
| Transcript | 인식 수행 시점 | 원본 삭제 시 함께 지울지 |
| Diarization 결과 | 화자 분리 시점 | 회의 기록과 연결·삭제 범위 |
| 누적 speaker profile | 프로필 생성·갱신 시점 | 여러 회의와의 관계, 삭제 전파, 수정·보존 |

하나의 “로컬 저장” 문구로 모든 데이터 정책을 대체하지 않는다. Damso의 처리 위치는 미확인이며 Sokki의 설명을 가져와 채우지 않는다.

## 사용자 승인과 참석자 동의

사용자에게 묻는 gate와 참석자에게 고지하고 동의를 확인하는 절차를 요구사항에서 분리한다. 참석자 동의가 필요한 환경이라면 고지 방식, 확인 대상, 철회 처리, 시작 조건을 별도로 정의해야 한다. 제공 자료는 해당 절차나 법적 적합성을 입증하지 않는다.

## 평가 해석

- 감지 횟수, 승인·거부 수, 반복 질문 수, 승인 소요 시간을 구분해 기록한다.
- **거부율 ≠ 오탐률:** 실제 회의라도 기록을 원하지 않아 거부할 수 있다.
- 오탐 평가에는 회의 여부에 대한 별도 ground truth와 평가 단위가 필요하다.
- 로그에도 오디오나 발화 내용을 불필요하게 포함하지 않도록 데이터 범위를 정한다.
