# Projects: 지속 실행 업무 실습

아래는 dossier에서 도출한 프로젝트 제안이다. 소개 도구의 확정 기능이나 실행 보장을 뜻하지 않는다.

## 1. 사용자 부재 중 리서치

- **출발점**: Dots의 작업 연속성, Grok Bot의 리서치 역할.
- **범위**: 사용자가 제공한 문서 묶음의 쟁점 정리와 보고서 초안.
- **산출물**: 쟁점별 근거 표, 초안, 미완료 목록, 실행 관찰 기록.
- **완료 기준**: 결과의 근거를 대조할 수 있고 미완료 상태가 구별된다. 이탈 중 진행은 별도 기록으로 평가한다.

## 2. 채팅 기반 운영 요청 처리

- **출발점**: OpenClaw의 백그라운드 서비스·채팅 요청 처리.
- **범위**: 상태 조회나 보고서 생성처럼 검토하기 쉬운 요청.
- **산출물**: 요청 식별자, 입력, 처리 상태, 결과를 대응시킨 기록.
- **완료 기준**: 누락·중복·실패를 식별할 수 있다. 기록 기능을 지원하지 않으면 실험자가 수동 관리한다.

아래는 실습용 기록 모델이며 제품 API 또는 실제 상태 체계가 아니다.

```text
request_id | received_at | observed_status | result | error
```

## 3. 연구자·작성자·검토자 workflow

- **출발점**: Hermes의 역할 구성.
- **범위**: 근거 정리 → 초안 → 원문 대조 검토.
- **산출물**: 단계별 파일과 전달 기록, 검토 후 수정본.
- **완료 기준**: 오류가 발생한 단계를 추적하고, 근거에 없는 주장을 표시·수정한다.

처음에는 수동으로 전달해도 된다. 자동 전달과 검토 강제성은 별도 검증한다.

## 4. 일상 업무·장기 목표 관리

- **출발점**: Muse의 알림·장기 목표 활용.
- **범위**: 목표를 작은 작업으로 나누고 진행 상황 기록.
- **산출물**: 목표·작업 목록, 계획 시각, 실제 실행 기록.
- **완료 기준**: 목표 정보 보관과 예정 시점의 실제 실행을 따로 판정한다.

예약·쇼핑·양식 제출로 확장할 때는 실행 권한과 승인 방식을 먼저 확인한다. 장기 목표가 저장되어 있다는 사실만으로 scheduler 또는 상시 실행을 입증할 수 없다.

## 공통 평가

- [ ] 입력·예상 산출물·완료 조건을 실행 전에 정했다.
- [ ] 관찰 사실, 수동 보완, 제품 지원 기능을 구분했다.
- [ ] 실패·미완료와 근거 부족을 기록했다.
- [ ] 한 번의 성공을 장기 실행 보장으로 일반화하지 않았다.
