# 심화 학습: 상시 운영과 장애 구분

## 세 가지 검증 축

| 축 | 질문 | 학습용 증거 |
|---|---|---|
| 기능 | 입력에 맞는 응답인가 | 입력·실행 결과·수신 결과 |
| 접속 | 필요한 웹앱 경로에 접근 가능한가 | 주소·시간·실패 메시지 |
| 상시 운영 | 작업자 조작 없이 계속 실행되는가 | 관찰 구간·실행 기록·중단 이력 |

영상에는 접속 실패와 80·443 및 ports 항목이 등장하지만 원인과 해결 결과는 없다. 문의 수신 채널도 불명이므로 해당 접속 문제가 자동 응답의 장애였다고 확정할 수 없다.

## 접속 실패 조사 연습

1. 실패한 URL, 시각, 메시지를 기록한다.
2. 앱 프로세스와 실제 Listen port를 확인한다.
3. Container 사용이 확인된 경우에만 Port mapping을 조사한다.
4. 실제 구성에 있는 Proxy·네트워크 접근 규칙을 경로별로 확인한다.
5. 변경 전후 같은 요청을 재실행해 결과를 비교한다.

이는 일반적인 조사 제안이다. 방화벽 개방이나 80·443 설정 변경을 일괄 해결책으로 적용하지 않는다.

## 상시 운영 관찰 계획

- 관찰 기간과 테스트 입력 횟수를 먼저 정한다.
- 작업자가 개입하지 않은 동안에도 실행되는지 확인한다.
- 중단·복구 시점과 응답 누락 여부를 기록한다.
- 재시도나 중복 처리가 필요하면 정책을 명시하고 별도로 시험한다.
- 자원 사용량과 비용을 직접 측정하며 영상 사양으로 처리량을 추정하지 않는다.

위 항목은 운영 설계 제안이며 영상에서 확인된 기능이 아니다. 한 번의 성공이나 짧은 관찰만으로 장기 가용성을 보장할 수 없다.

## 연동 검토

Twenty의 어떤 고객 정보가 문의 처리에 필요한지 먼저 정한다. API·인증·권한·실행 결과를 확인한 연결만 구조도에 넣는다. Docker 실행, Coolify 배포 역시 사용 증거가 있을 때만 실제 구성으로 기록한다.
