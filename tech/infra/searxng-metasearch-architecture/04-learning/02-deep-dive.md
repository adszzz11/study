# Deep Dive: 결과 통합과 운영 경계

> 이 노트는 제공된 dossier와 기존 지식에 기반한 초안이다. 제품 기능·구현·지원 범위는 **확인 필요**이며, 최신 버전·운영 상태·성능 수치를 주장하지 않는다.

## 결과 통합의 다섯 과제

| 과제 | 실험 포인트 | 해석 주의 |
|---|---|---|
| 중복 | URL 변형·추적 파라미터가 다른 동일 문서 비교 | 정규화가 서로 다른 페이지를 합칠 수 있음 |
| 순위 | 엔진별 상위 결과와 통합 순위 비교 | 엔진 간 점수는 직접 비교하기 어려움 |
| 필드 정규화 | 제목·URL·snippet·날짜 누락 관찰 | 누락과 파싱 실패를 구분 |
| 소스 편중 | 엔진별 결과 수와 상위 노출 비중 비교 | 결과 수가 품질을 뜻하지 않음 |
| 부분 실패 | 실패 엔진이 있을 때 응답·오류 표시 관찰 | 성공 응답만으로 모든 소스 성공을 추정하지 않음 |

이 표는 일반적인 Metasearch 과제다. SearXNG의 실제 알고리즘과 설정은 **확인 필요**다.

## Latency와 검색 범위

병렬 호출 후 모든 엔진을 기다리는 모델에서는 느린 엔진이 전체 지연을 좌우한다. 개념적으로 `T_total ≈ max(T_engine) + T_merge`로 생각할 수 있지만, 이는 SearXNG의 구현이나 성능 공식이 아니다. timeout을 줄이면 대기 시간을 제한하면서 결과 범위를 줄일 수 있다.

- 엔진 수를 바꿀 때 유용한 결과 비율·응답 시간·외부 요청량·실패율을 함께 기록한다.
- 동일 질의 집합과 유사한 언어·지역·시점 조건에서 비교한다.
- 동시성·timeout·장애 처리의 실제 지원 범위를 먼저 확인한다.

## Privacy 데이터 경로 점검

```text
브라우저 → Reverse Proxy → 애플리케이션 → 외부 검색 엔진
             ↓                  ↓
          접근 로그          앱 로그 / 모니터링
```

각 단계에서 질의·IP·시간·헤더가 기록되는지, 누가 접근하며 언제 삭제하는지 확인한다. URL에 담긴 질의가 Proxy 로그에 남는지도 점검한다. 기본 로그·쿠키·헤더 처리 정책은 **확인 필요**다.

## 공개 범위별 운영 설계

| 항목 | Private | Public |
|---|---|---|
| 접근 | 인증·네트워크 경계 | 익명·자동화 요청 정책 |
| 요청량 | 팀 사용량 기반 | abuse와 급증 고려 |
| 장애 | 내부 안내·복구 절차 | 사용자 오류 표시·운영 대응 |
| 로그 | 최소 수집·접근 제한 | 대응 필요성과 최소 수집의 균형 |

인증·Rate Limiting 등의 내장 여부는 가정하지 않는다. 필요한 제어를 어느 계층에서 제공하는지 문서와 배포 구성으로 확인한다.
